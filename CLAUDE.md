# CLAUDE.md

## Project Overview

This is a GitHub Pages static site (`mmtduzz.github.io`) that serves the **EcoSnap Base64** tool — a browser-based utility that converts image files to Base64-encoded strings for use inside Thunkable mobile apps via the WebViewer component.

There is no build system, no framework, and no package manager. Everything is plain HTML and vanilla JavaScript.

## Repository Structure

```
mmtduzz.github.io/
├── index.html       # Main Base64 converter (primary entry point)
├── encode.html      # Alternate version generated by Cocoa HTML Writer
├── EcoSnapBase64    # Standalone HTML snippet (no .html extension)
└── README.md        # Minimal project description
```

### File Descriptions

| File | Purpose |
|---|---|
| `index.html` | Primary page. Accepts an image via `<input type="file">`, reads it with `FileReader`, strips the data URI prefix, and calls `window.ReactNativeWebView.postMessage(base64String)` to send the result back to the Thunkable app. |
| `encode.html` | Older/alternative version exported from Cocoa (macOS HTML Writer). Uses `ThunkableWebviewerExtension.postMessage(base64String)` — a different Thunkable bridge API. The HTML source is embedded as escaped text inside an HTML4 wrapper. |
| `EcoSnapBase64` | A standalone HTML file (no extension) that does both: displays the Base64 string in the DOM (`<p id="output">`) and sends it via `window.ReactNativeWebView.postMessage()`. Useful for debugging. |

## Integration Pattern

All files share the same core pattern:

1. A hidden or visible `<input type="file" accept="image/*">` triggers image selection.
2. A `FileReader` reads the image as a data URL.
3. The Base64 payload is extracted by stripping the `data:<mime>;base64,` prefix.
4. The payload is sent to the host Thunkable app via one of two bridge APIs:
   - `window.ReactNativeWebView.postMessage(base64String)` — React Native bridge (modern Thunkable)
   - `ThunkableWebviewerExtension.postMessage(base64String)` — legacy Thunkable WebViewer bridge

## Development Workflow

### No build step required

Files are plain HTML. Open directly in a browser for local testing:

```bash
# Open directly — no server needed for basic testing
open index.html
```

For testing the `postMessage` integration, you must load the page inside a Thunkable WebViewer component, as the bridge objects (`window.ReactNativeWebView`, `ThunkableWebviewerExtension`) only exist in that context.

### Deployment

The site is hosted on **GitHub Pages** and served directly from the `main` branch root. Pushing to `main` triggers an automatic deployment — no CI pipeline, no build artifacts.

```bash
# Typical deploy flow
git add <file>
git commit -m "Description of change"
git push origin main
```

### Development Branch Convention

Active work should happen on feature branches. The naming pattern used in this repo is:

```
claude/<short-description>-<id>
```

Example: `claude/add-claude-documentation-GDLa7`

## Code Conventions

- **Language**: Turkish comments appear in the source code (e.g., `// Dosya seçildiğinde çalışacak olay dinleyici` = "Event listener that runs when file is selected"). Maintain Turkish for inline comments if editing existing files; use English for new comments.
- **No framework**: Do not introduce React, Vue, bundlers, or any npm dependencies. This is intentionally dependency-free.
- **No styling**: The existing pages have minimal or no CSS. Do not add styling unless explicitly requested.
- **Keep it minimal**: Each page does one thing. Avoid adding features beyond what is asked.
- **Thunkable bridges**: Both `window.ReactNativeWebView` and `ThunkableWebviewerExtension` should be guarded with existence checks before calling, since they are undefined in a normal browser context.

## Key Constraints

- Do not introduce a `package.json`, bundler, or any build tooling.
- Do not rename `EcoSnapBase64` to add an `.html` extension unless the Thunkable app's WebViewer URL is also updated.
- The site must remain compatible with the GitHub Pages free tier (static files only, no server-side logic).
- Avoid breaking the `postMessage` integration — it is the sole output channel for the mobile app.
